# 实验 2-3 观察 — 四件值得记的事

## 1. 两种错误模式的危害类型**完全不同**，这比数字本身重要

| | `dynamic_system` | `sliding_window` |
|---|---|---|
| 任务 | ✅ **照常完成** | ❌ **失败** |
| 轮数 / 工具调用 | 9 / 30（与基线**完全一致**） | 30（触顶）/ 82 |
| 重复调用 | 0 | **32 次**（同工具同参数） |
| 代价 | **缓存 70.6% → 0.6%，账单 3.3 倍** | 陷入循环，任务做不完 |

**往 system 里注入动态内容，输出看不出任何异常**——同样 9 轮、同样 30 次工具调用、同样完成任务、零重复。
它唯一的代价是钱和延迟，而这两样都不会出现在 Agent 的回答里。

> 这就是书里说的「**无形成本**」：开发者写下一行看似无害的代码，让整条链路慢一个量级，而**没有任何东西会报错**。

对照第一章那条：**「给出了回答」≠「完成了任务」**。这里是它的反面——
**任务确实完成了，但你正在为它付 3 倍的钱，而且你不会知道。**

## 2. 滑动窗口的失败方式，和书里预言的一模一样

书里说：*"使用滑动窗口的 Agent 经常陷入循环，反复执行相同的工具调用，因为它'忘记'了之前已经获得的结果。"*

实测：**82 次工具调用里有 32 次是重复的**（同一个工具、完全相同的参数），日志里连续出现

```
✓ find: Found 0 files
✓ find: Found 0 files
✓ find: Found 0 files
...
```

它一遍遍重跑同一个查不到东西的搜索，因为结果已经滑出窗口了。最终撞上 30 轮上限，**任务失败**。

**所以滑动窗口的主要危害根本不是缓存**（它的缓存占比 12.3%，比 `dynamic_system` 的 0.6% 还高），**而是丢信息**。
书里把它和 `text_format` 一起单列出来强调"危害不止于缓存"，这次实测把这一点坐实了。

## 3. ⚠️ 缓存省钱很明显，省延迟没那么明显 —— 而书里其实解释过

逐轮 TTFT 对比里，`dynamic_system` 只比 `correct` 慢 1.0–2.1 倍，没有出现书里开头故事那种 6–10 倍的差距。
更值得注意的是：**`correct` 自己的 TTFT 也从 6s 涨到了 126s**，尽管它缓存命中率 70%。

书里第二章有一句容易被跳过的话，正好解释这件事：

> KV Cache 省去的是历史 token 的 **K、V 投影重算**，使每步解码不必重算整个前缀；
> **但每个新 token 的注意力计算仍要遍历全部缓存的 K、V，计算量随上下文长度线性增长。**

也就是说：**缓存消掉的是"重算前缀"那部分，消不掉"注意力要扫过全部上下文"那部分。**
所以上下文一长，即使全部命中缓存，延迟照样上去。

**结论修正**：不要指望"保持前缀稳定"能解决长上下文的延迟问题——
它主要解决的是**成本**（本次实测 3.3 倍）。延迟要靠**压缩和隔离**去解决，那是另一套手段。

## 4. 读指标要看口径 —— 工具打印的 "Cache Hit Rate: 100%" 是误导

三组跑下来，**每一组**的输出里都写着 `Cache Hit Rate: 100.0%`，包括缓存占比只有 **0.6%** 的那组。

原因：这个 "hit rate" 统计的是**有多少次调用命中了哪怕一点缓存**，而不是**多少比例的 token 命中了缓存**。
真正有意义的指标是它下面那行 **`Cache Ratio: X% of prompt tokens cached`**。

🧩 这和第三章那个脚注是同一类陷阱：书里的 `recall@k` 其实是**命中率 hit rate**，而不是学术定义的召回率。
**同一个词在不同地方口径不同——跨来源比较指标之前，先确认它到底在数什么。**

## 工程教训（和实验内容无关，但真实发生了）

第一次用 `--compare` 一口气跑六组，结果：
1. 机器**半夜休眠**，第 14 轮隔了 8 小时才报 Connection error，后面几组醒来后网络未恢复直接失败
2. 最后进程被系统以**内存不足**杀掉

改成**一次只跑一个模式**就全部顺利。长跑实验不要留给夜里，也不要一次串六个。
